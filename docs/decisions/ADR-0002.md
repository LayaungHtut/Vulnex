# ADR-0002: Repository layout and toolchain

- **Status:** PROPOSED (prepared under founder decision D6, 2026-11-06). Not approved and not implemented.
- **Date:** 2026-11-06 · **Author:** Claude · **Approver:** Founder · **Reviewers:** Astra 6; GPT-6 when available
- **Depends on:** [ADR-0001](ADR-0001.md) (one control-plane deployable, one worker deployable)

## Context

Today the repository root is a SvelteKit app. VULNEX will add a Python control plane, a Python scanner worker and their shared wire protocol. The founder's sketch (Master Instructions §18) lists `apps/`, `engines/`, `packages/` and other folders, and also says "do not create empty directories to look sophisticated." The founder's machine is a 16 GB Windows laptop. CI will be GitHub Actions (D8).

## Problem

Where does each component live, and which tools build, lint and test it, so that one command checks everything and the layout matches ADR-0001's deployables?

## Alternatives considered

1. **Keep SvelteKit at the root and add `engines/` beside it.** This is the smallest diff today. But the JavaScript configs (vite, svelte, playwright, eslint, tsconfig) would keep claiming the whole repository, so ESLint, Prettier and svelte-check would scan Python folders and fixtures, and the root would serve two masters. Rejected.
2. **Separate repositories per component.** This gives independent release cycles, but the API and the worker must stay protocol-compatible, so changes to both would need cross-repository coordination. That is too much overhead for one founder. Rejected.
3. **One monorepo: JS app under `apps/console`, Python under `engines/`, one shared protocol package.** Recommended.

## Decision (proposed)

```
apps/console/               SvelteKit app (moved with git mv; keeps history)
engines/api/                Control plane, Python package `vulnex` (ADR-0001 modules)
engines/scanner/            Worker, Python package `vulnex_scanner`
packages/worker-protocol/   Python package `vulnex_worker_protocol`: Pydantic models for /worker/v1
deploy/compose/             Docker Compose reference stack (created in Phase 2)
docs/                       As today
package.json                npm workspace root: Prettier for docs + scripts that delegate to apps/console
pyproject.toml              uv workspace root (members: engines/*, packages/*), shared ruff/mypy config
uv.lock, package-lock.json  Both committed
.python-version             3.13
```

- Directories are created only when their first real file lands. Phase 2 creates `engines/api`, `engines/scanner`, `packages/worker-protocol` and `deploy/compose`. `plugins/`, `scripts/` and a root `tests/` wait until something needs them. First-party plugins live in `engines/scanner/plugins/` until a separate plugin release cycle exists.
- **JavaScript toolchain:** npm workspaces (`"workspaces": ["apps/*"]`). Node 24 (pinned via `engines` and `.nvmrc`). Prettier stays at the root so docs are formatted in one place. ESLint, svelte-check, Vitest and Playwright run inside `apps/console`.
- **Python toolchain:** [uv](https://docs.astral.sh/uv/) workspace with one lockfile, plus `ruff` (lint and format), `mypy --strict`, `pytest`, and `import-linter` to enforce ADR-0001 module boundaries. Python 3.13 is already installed on the founder's machine. Database tests run against real PostgreSQL in Docker, never SQLite, because RLS behaviour is under test (ADR-0005).
- **Single entry points:** `npm run lint` / `npm run check` / `npm test` at the root delegate to the workspace. For Python, `uv run ruff check`, `uv run mypy`, `uv run pytest`. CI runs both.
- **Vendored AI-tool folders** (`.claude`, `.cursor`, `.gemini`, `.github/agents`, `.github/skills`, `.opencode`, `.pi`) stay at the root and are excluded from Prettier (founder D9). They are not VULNEX source.

## Consequences

- One `git mv src static vite.config.ts svelte.config.* playwright.config.ts tsconfig.json eslint.config.js package.json → apps/console/` commit, plus a new root `package.json`. The `.vscode` settings and `AGENTS.md` paths need checking afterwards.
- `adapter-auto` → `adapter-node` happens in the same phase (self-hosted packaging, D2).
- Two package managers (npm, uv). That is unavoidable with a TypeScript frontend and Python backend, and both are fast on the laptop.
- `packages/worker-protocol` is the only code shared between deployables. Its version is part of the worker compatibility check (PRD §17).

## Security implications

- Both lockfiles are committed and CI installs with `npm ci` / `uv sync --locked`, so dependency drift becomes a reviewable diff (THREAT_MODEL TM-8-4).
- Separate packages make it harder for scanner code to import control-plane internals (secrets, database), and import-linter checks it.
- No secrets in the repository. `.env*` is already git-ignored except `.env.example`/`.env.test`. Secret scanning runs in CI (D8).

## Migration considerations

- History is kept by `git mv`. Open branches touching the SvelteKit root need rebasing. There are none today.
- If a component later needs its own repository, the folder boundary makes `git filter-repo` extraction straightforward.
