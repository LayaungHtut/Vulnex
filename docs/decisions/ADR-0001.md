# ADR-0001: Modular monolith control plane with separately deployed scanner workers

- **Status:** PROPOSED. The direction comes from the founder's Master Project Instructions §10 ("A modular monolith is the default starting point for the control plane. Scanner workers may be independently deployed."). The concrete boundaries below are Claude's proposal. On 2026-11-06 the founder conditionally approved this direction (D5/D6) and asked to inspect this ADR before formally approving it. Astra 6 has not reviewed it.
- **Date:** 2026-11-06 · **Author:** Claude · **Approver:** Founder · **Reviewers:** Astra 6; GPT-6 when available

## Context

VULNEX needs a control plane (identity, tenancy, assets, scans, findings, reporting), an intelligence plane (feed ingestion, correlation) and a scanning plane (probes inside customer networks). The team is one founder plus AI agents, with a 16 GB laptop and no infrastructure budget. All three deployment modes (SaaS, self-hosted, hybrid) must stay possible.

## Problem

How many deployable units should v0 have, and where do the plane boundaries sit?

## Alternatives considered

1. **One process for everything, including scanning.** This is the simplest option. But scanning has to run inside customer networks for the hybrid mode, needs different privileges and resource limits, and its failures must not take down the API. Rejected.
2. **Microservices per plane or per domain** (separate identity, asset, scan, intel and risk services, connected by a broker). This gives independent scaling and deploys, but multiplies the services to secure, deploy, version and debug, and needs distributed transactions for lease and result handling. Nothing measured justifies it. Rejected for v0.
3. **Modular monolith control plane with intelligence and risk as internal modules, plus a separate scanner worker.** This is the proposal.

## Decision (proposed)

- **One control-plane codebase and image** (`engines/api`) with internal modules: identity/tenancy, assets/scope, scans/queue, findings/remediation, intelligence, risk, reports/audit. It runs as two processes from the same image: the HTTP API, and a background runner for schedules, ingestion, exports and retention.
- Modules call each other only through their public Python interfaces. They do not import each other's tables or internals. The risk module is pure, with no I/O.
- **One scanner worker codebase and image** (`engines/scanner`), deployed independently. It talks to the control plane only through the versioned `/worker/v1` protocol over outbound mTLS.
- The only shared code is the worker protocol models (`packages/worker-protocol`).

## Consequences

- One database, one migration stream and one deploy for the control plane. Cross-module changes can be transactional.
- Module discipline is a convention. It is backed by import-lint rules (for example `import-linter`) but not by process isolation. Discipline lapses would make a future split harder.
- Worker and control plane must keep protocol compatibility across versions (PRD §17: current and previous minor).
- Scaling: workers scale out independently. The control plane scales vertically first, then horizontally behind a load balancer, since it is stateless apart from PostgreSQL.

## Security implications

- The control plane is a single high-value process. A remote code execution flaw there reaches every module, so dependency hygiene and input validation carry more weight.
- Workers are a separate trust zone with their own identity and no database access. This is the main blast-radius control for compromised customer-side hosts (THREAT_MODEL TB3/TB4).
- Intelligence ingestion runs in the background runner, not the request path, so malformed feed content cannot block API requests. It still shares the database and must treat feed data as untrusted (TB6).

## Migration considerations

- A module can be extracted into a service later behind its existing interface, if measured load or team boundaries justify it. Extracting the intelligence plane first is the most likely candidate, because it is tenant-free and read-mostly.
- Nothing in v0 depends on in-process calls between the worker and the control plane, so the worker boundary is already a network boundary.
