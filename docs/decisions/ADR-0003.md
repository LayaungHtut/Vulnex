# ADR-0003: Job transport — PostgreSQL pull queue

- **Status:** PROPOSED. Implemented on `feature/m4-scanner` for review; not approved.
- **Date:** 2026-11-08 · **Author:** Claude · **Approver:** Founder · **Reviewers:** Astra 6
- **Addresses founder D6 conditions:** (a) job claiming, leases, retries, idempotency; (b) cancellation and stale-job recovery
- **Related:** [INITIAL_ARCHITECTURE §7.1](../architecture/INITIAL_ARCHITECTURE.md) (the detailed semantics this ADR adopts) · [ADR-0001](ADR-0001.md) · [ADR-0005](ADR-0005.md) · [ADR-0006](ADR-0006.md) §6 (heartbeat and lease timing)

## Context

Scans run on separately deployed workers that connect out to the control plane and must not touch the database (ADR-0001, ADR-0006). The control plane needs a durable way to hand out work, notice when a worker disappears, retry, cancel, and accept results exactly once in effect. Founder D5/D6 conditionally approved "a PostgreSQL-backed job queue" and asked that Redis, RabbitMQ or NATS not be added without a demonstrated need (Master Operating Prompt §7.3).

## Problem

Choose the job transport, and define delivery guarantees, claiming, leases, retries, cancellation, recovery and result handling precisely enough to test.

## Alternatives considered

| Option                                                                   | Assessment                                                                                                                                                                                               |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **PostgreSQL table + `FOR UPDATE SKIP LOCKED`, workers pull over HTTPS** | No new service; state changes and results commit in the same transaction as the business data; one backup covers everything. Throughput ceiling is far above v0 needs (to be measured). **Chosen**       |
| Redis (lists/streams)                                                    | Extra service and memory on a 16 GB laptop; results still need a second, non-atomic write to PostgreSQL. Rejected for v0                                                                                 |
| RabbitMQ / NATS JetStream                                                | Mature delivery semantics, but a second durable store to operate, secure and back up; workers would need a broker credential in customer networks. Rejected for v0; revisit if measured load requires it |
| Library queues (procrastinate, pgmq, River-style)                        | Close to the chosen design, but they assume the consumer has a database connection; VULNEX workers must not. Their claim SQL is the same idea. Not adopted, to keep the worker boundary                  |

## Decision (proposed)

Adopt INITIAL_ARCHITECTURE §7.1 as written: **at-least-once delivery with idempotent effects**, a `queue.job` table, claim with `FOR UPDATE SKIP LOCKED`, a fresh random `lease_id` per claim, lease extension carrying the cancel flag, results keyed by `(job_id, attempt, seq)`, completion in the same transaction as the final result, exponential backoff with jitter (30 s base, doubling, 15 min cap), `dead` after `max_attempts`, and a sweeper for expired leases. All times come from the database clock.

Refinements made while implementing (each is a deliberate choice for review):

1. **No separate `vulnex_queue` role.** §7.1 proposed a dedicated owner role. The implementation uses the M2 pattern instead: schema `queue` owned by `vulnex_owner`, **no table privileges** for `vulnex_app`, access only through `SECURITY DEFINER` functions with a fixed `search_path`. The isolation is the same (the application role cannot read or write queue rows directly), and it avoids changing the role-creation script, which only runs on an empty database volume.
2. **Idempotency keys are per tenant.** A unique index on `(tenant, queue, idempotency_key)` for jobs that have a key (global jobs share one namespace) instead of `(queue, idempotency_key)`, so one tenant cannot block or detect another tenant's key.
3. **Enqueue takes the tenant from the session context**, never from a parameter: `queue.enqueue_scan_task` uses `app.current_tenant()` and checks the scope group inside that tenant.
4. **A fourth terminal outcome, `refused` → state `failed`, never retried.** A worker that refuses a task (for example, its scope lease fails verification) reports `refused`; retrying a task the worker has already judged unsafe adds nothing. Ordinary `failed` outcomes and expired leases are retried.
5. **Stale workers are derived, not stored.** `app.worker.status` is `active`, `disabled` or `revoked`; "stale" is computed from `last_seen_at` (ADR-0006 §6: 30 s), which removes a sweeper write per worker. Claiming requires `active`.
6. **Duplicate detection includes the lease.** A result row stores the `lease_id` it was accepted under, and "duplicate" is only reported to a caller presenting that same lease. A caller without the lease learns nothing about which results exist.

Functions (all `SECURITY DEFINER`, callable only by `vulnex_app`):

| Function                                                                                          | Caller                                                       | Effect                                                                             |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `queue.enqueue_scan_task(scope_group_id, kind, payload, idempotency_key, priority, max_attempts)` | API, tenant context                                          | Insert or return the existing job for the key                                      |
| `queue.claim_for_worker(worker_id, n, ttl)`                                                       | worker API; `worker_id` from the authenticated identity only | Lease up to `n` (≤10) jobs of the worker's tenant and scope group                  |
| `queue.extend(job_id, lease_id, worker_id, ttl)`                                                  | worker API                                                   | Extend an unexpired lease; returns the cancel flag                                 |
| `queue.submit_result(job_id, lease_id, worker_id, attempt, seq, payload)`                         | worker API                                                   | `accepted` / `duplicate` / `stale` (stale payloads are quarantined, never applied) |
| `queue.complete(job_id, lease_id, worker_id, attempt, seq, payload, outcome, error)`              | worker API                                                   | Final result and state change in one transaction                                   |
| `queue.request_cancel(job_id)`                                                                    | API, tenant context                                          | `queued` → `cancelled`; `leased` → cancel requested                                |
| `queue.sweep()`                                                                                   | background runner                                            | Expired leases → retry, `cancelled` or `dead`                                      |

## Consequences

- No new infrastructure. Queue state survives restarts of the API and of workers; nothing is held in process memory.
- Delivery is at-least-once: a worker may receive a job again after its lease expired. Correctness depends on results being keyed by attempt and on scan results being treated as observations of a specific attempt (PRD §13).
- Long-polling workers hold API connections; the database connection is held only during each claim attempt, not for the whole poll.
- The fairness cap per tenant is designed (§7.1) but not implemented; v0 self-hosted is effectively single-tenant (D2).

## Security implications

- The application role has no direct access to queue rows; every path is a reviewed function. A compromised API process can still call the functions, so worker identity (ADR-0006 §2) must be established before `claim_for_worker` is called and must never come from a request body.
- A job can only be claimed by a worker in the same tenant **and** scope group, checked inside the claim function against `app.worker`, which is itself under row-level security for the caller's tenant context.
- The lease ID is a random 122-bit secret held by the current lease holder; results without it are quarantined.
- Quarantined payloads are attacker-influenced data from possibly stale or revoked workers: they are stored for audit only and must never be parsed into findings.

## Migration considerations

Migration `0004` adds schema `queue`, `app.worker`, and the functions. Downgrade drops them and all queued work. Moving to a broker later would replace the functions behind the same worker HTTP protocol; workers would not change.

## Required tests (implemented in `engines/api/tests/test_queue_db.py`)

Concurrent claimers never share a job · claims stay inside the worker's tenant and scope group, and disabled or revoked workers get nothing · expired lease → retried with backoff · duplicate result has no effect · late result after re-lease → stale and quarantined · cancel queued, cancel leased with the worker acknowledging, cancel leased with the worker gone · retries end in `dead` · refused is not retried · completion always stores its final result · concurrent sweepers handle each job once · idempotent enqueue per tenant · the application role cannot touch queue tables directly. **Not yet done:** the load test (10,000 queued jobs, 4 claimers) from §7.1.
