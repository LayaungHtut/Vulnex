# ADR-0006: Scanner worker trust, signed scope and destination validation

- **Status:** PROPOSED (prepared under founder decision D6, 2026-11-06). Not approved and not implemented.
- **Date:** 2026-11-06 · **Author:** Claude · **Approver:** Founder · **Reviewers:** Astra 6 (security review requested); GPT-6 when available
- **Addresses founder D6 conditions:** (e) scanner authentication, revocation and signed scope verification; (f) DNS resolution, IPv4/IPv6, redirects and address validation
- **Related:** PRD Amendment A2, §12, SEC-04/05/08, AC-07 · THREAT_MODEL TB3, TB4 · [ADR-0001](ADR-0001.md), [ADR-0005](ADR-0005.md) · queue semantics in [INITIAL_ARCHITECTURE §7.1](../architecture/INITIAL_ARCHITECTURE.md)

## Context

Workers run inside customer networks and connect **out** to the control plane (D2 hybrid model, ADR-0001). A worker is the one VULNEX component that can send packets to real systems. If its identity is stolen, or its scope is wrong, VULNEX scans something it has no authorization to touch. The founder requires that the worker **enforce authorized scope independently** (Master Instructions §15).

## Problem

1. How does a worker prove who it is, and how is that revoked?
2. How does a worker know, independently, what it may touch?
3. How is every destination validated, including DNS answers, IPv6 forms, redirects and odd address notations, so that a scan cannot be steered outside scope?

## Alternatives considered

| Topic            | Option                                                                                                              | Assessment                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker auth      | Static API key                                                                                                      | Simple, but a long-lived bearer secret that can be copied off the host. Rejected                                                                |
|                  | OAuth client credentials                                                                                            | Needs a token service; still bearer tokens. Rejected for v0                                                                                     |
|                  | **mTLS with a short-lived client certificate whose key never leaves the host**                                      | Recommended                                                                                                                                     |
| mTLS termination | **Caddy verifies the client certificate and forwards its fingerprint over the internal network**                    | Recommended for v0. Caddy is already in the stack for TLS, so no new infrastructure                                                             |
|                  | uvicorn terminates TLS directly                                                                                     | Simpler trust chain, but I could not confirm that uvicorn exposes the peer certificate to the ASGI app (UNVERIFIED, R7). Re-evaluate if it does |
| Scope delivery   | Unsigned scope in the lease response                                                                                | Integrity depends entirely on the transport and API path                                                                                        |
|                  | **Ed25519-signed scope lease, verified over the exact received bytes, plus an optional worker-local scope ceiling** | Recommended                                                                                                                                     |
| Revocation       | CRL/OCSP                                                                                                            | Extra infrastructure. Rejected; v0 checks the worker record on every request instead                                                            |

## Decision (proposed)

### 1. Enrollment

1. An Owner/Admin creates an **enrollment bundle**: `{control_plane_url, ca_sha256, token}`. The token is 256-bit random, single-use and expires within 24 hours. Only its SHA-256 hash is stored, it is bound to one tenant and one scope group, it can be revoked before use, and its creation is audited.
2. `ca_sha256` pins the control plane's TLS CA, so a self-hosted install with a private CA can be trusted without trust-on-first-use.
3. The worker generates an **ECDSA P-256 key pair** locally. P-256 is chosen for compatibility across Python `ssl`, OpenSSL and Caddy. The worker stores the private key with owner-only file permissions and never transmits it.
4. The worker calls `POST /worker/v1/enroll` with the token and a CSR. The API checks the token (unused, unexpired, unrevoked), creates the worker record, and returns:
   - a client certificate from the deployment's **worker CA**: 7-day lifetime, SAN `urn:vulnex:worker:<worker_id>`;
   - the current and next **scope-signing public keys** with key IDs;
   - the protocol version range.
     The token is marked used in the same transaction.
5. **Renewal:** at 50% of the certificate's lifetime the worker sends a fresh CSR over its current mTLS session, generated from the same key or a rotated one. An expired certificate cannot renew, so the worker must re-enroll with a new token.

### 2. Authentication on every request

- Caddy terminates TLS for the worker endpoint with client authentication `verify_if_given` against the worker CA only. It strips any inbound `X-Vulnex-Client-Cert-Sha256` header and sets that header from the verified certificate.
- The API's worker routes listen on a **separate port bound to the internal Docker network only**, never published. They trust the header only on that listener. Every route except `/worker/v1/enroll` requires the header.
- The fingerprint is resolved through `app.worker_by_cert_fingerprint()` (ADR-0005), which sets the tenant context.
  - `active`/`stale`: allowed.
  - `disabled`: heartbeats allowed, no leases.
  - `revoked`: 401 on everything.
- UNVERIFIED for Astra 6: the exact Caddy client-certificate placeholders and header-stripping configuration. Note that R7 now also covers mTLS termination.

### 3. Revocation

An Owner/Admin revokes a worker in one transaction:

1. The worker record becomes `revoked` (terminal).
2. All its certificate fingerprints are marked revoked.
3. Every job leased to it gets `cancel_requested` and its `lease_id` invalidated, so any later result is rejected (§7.1).
4. An audit event is written.

The effect is immediate on the worker's next request, with no CRL distribution. When a worker receives 401 `revoked`, it stops all probes and deletes its key material. Certificates are short-lived (7 days), which bounds the damage if the revocation record were ever lost from the database.

### 4. Signed scope lease

Every leased task carries a scope lease:

```json
{
	"v": 1,
	"kid": "scope-2026-11",
	"job_id": "…",
	"lease_id": "…",
	"attempt": 1,
	"tenant_id": "…",
	"worker_id": "…",
	"scope_group_id": "…",
	"not_before": "…Z",
	"expires_at": "…Z",
	"targets": ["10.0.5.0/28", "intranet.example.test"],
	"authorized_cidrs": ["10.0.0.0/16"],
	"exclusions": ["10.0.5.7/32"],
	"ports": [22, 80, 443],
	"primitives": ["tcp_connect", "tls_handshake", "http_get", "ssh_banner"],
	"limits": {
		"max_concurrency": 32,
		"max_rate_per_s": 100,
		"probe_timeout_s": 1,
		"task_timeout_s": 900
	},
	"plugin_bundle_sha256": "…",
	"profile_sha256": "…"
}
```

- The API signs the **exact JSON bytes** with Ed25519 and sends `payload_b64`, `sig_b64` and `kid`. The worker verifies the signature over those bytes **before** parsing them, so there is no JSON canonicalization step that two implementations could get wrong.
- Before running anything, the worker checks:
  - the signature, against a key ID it was given;
  - `worker_id` is itself and `tenant_id` is its enrolled tenant;
  - `job_id`/`lease_id`/`attempt` match the lease response;
  - the time window, with at most 2 minutes of clock skew allowed;
  - the plugin bundle digest matches the loaded, signature-verified bundle (ADR-0007).
    Any failure means the worker refuses the task and reports the reason.
- **Clock:** the worker compares its clock with the server `Date` header on each heartbeat. If skew exceeds 2 minutes, it refuses leases and reports `clock_skew`.
- **Key handling:** the scope-signing key is separate from the worker CA key and from the plugin-signing key. Its private key is a mounted secret file, never stored in the database. Rotation works by announcing the next key at enrollment and on `/worker/v1/keys` (a key set signed by the current key) before switching.
- **Worker-local scope ceiling (customer-controlled):** an optional file on the worker host lists the CIDRs and hostnames this worker may _ever_ touch. The effective scope is `lease ∩ ceiling`. **Recommended as mandatory for hybrid deployments**, because it is the one control the control plane cannot override.
- **What signing does and does not buy (stated plainly for review):**
  - It gives integrity of the authorization record from API to worker, independent of proxies.
  - It gives a persisted, verifiable record of exactly what was authorized (audit).
  - It gives a format that can later travel offline (air-gapped mode).
  - It does **not** protect against a fully compromised control plane, which holds the signing key. The local ceiling is the control for that case.

### 5. Destination validation (one code path)

All network access in the worker goes through one module, `connector`. Any other socket creation in worker or plugin code (`socket`, `asyncio.open_connection`, HTTP clients) is banned by lint rules and code review. The connector runs these steps for **every** connection, including redirects:

1. **Strict parsing.**
   - IPv4 only in canonical dotted-decimal. Integer, hex, octal and short forms (`2130706433`, `0x7f.1`, `0177.0.0.1`, `127.1`) are rejected.
   - CIDRs must have host bits zero.
   - Hostnames are IDNA-normalized to lowercase A-labels with length limits. A hostname that parses as an IP literal is rejected.
   - The same parser runs on the API side, when scope is defined and when targets are expanded.
2. **IPv6.**
   - v0 does not assess IPv6 (PRD §7). IPv6 literal targets are rejected at scope definition. Hostname resolution uses A records for probing.
   - AAAA answers are recorded as evidence and reported as a coverage gap ("IPv6 address observed, not assessed"), never silently dropped.
   - Wherever an IPv6 address appears (an AAAA answer, a redirect `Location`), forms that embed IPv4 are normalized to the embedded IPv4 address and checked against the deny-list for audit purposes. That covers IPv4-mapped `::ffff:0:0/96`, IPv4-compatible `::/96`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16` and Teredo `2001::/32`. The connection is still refused. When IPv6 support arrives, the same validator extends to IPv6 ranges.
3. **Never-allowed destinations**, which no scope can override:
   - `0.0.0.0/8`, `127.0.0.0/8`, `169.254.0.0/16` (link-local, including cloud metadata `169.254.169.254`);
   - `224.0.0.0/4`, `240.0.0.0/4`, `255.255.255.255/32`;
   - the control plane's resolved addresses, and the worker host's own interface addresses.
   - The list is maintained in code with tests. Other cloud-provider metadata addresses are added as identified (R7).
4. **Private and shared ranges** (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`) are allowed **only** when inside the lease's `authorized_cidrs`.
5. **Scope membership:** the address must be in the lease targets (or, for a hostname target, see step 6), inside `authorized_cidrs`, outside `exclusions`, inside the local ceiling if one is configured, and the port must be listed.
6. **DNS:**
   - The worker resolves names itself (system resolver by default, configurable). It records the name, resolver, CNAME chain, answers and time as evidence, and validates **every** answer.
   - It connects to the **validated IP**, never back to the name. TLS uses the hostname as SNI; HTTP sends it as `Host`. Pinning the IP this way defeats DNS rebinding between check and connect.
   - Each task resolves once and keeps that result for the task's duration. TTLs never extend authorization.
   - A hostname target's addresses must fall inside `authorized_cidrs`. Exception: a scope entry explicitly marked "external hostname, any public address", which requires an admin attestation. Even then, private, shared and never-allowed addresses are refused, so a hostname cannot be rebound to an internal address.
7. **Redirects:** primitives never follow redirects automatically. `http_get` returns the 3xx status and the `Location` header as evidence. Only a plugin whose manifest declares `follow_redirects: n` (at most 3) gets more hops. Each hop must be `http`/`https` and its host must pass steps 1–6 again. A hop that fails is recorded as "redirect out of scope" and the chain stops.
8. **Limits:** concurrency, rate, probe timeout, task timeout, maximum response bytes per probe (proposed 64 KiB) and total targets come from the lease and are enforced in the connector.

### 6. Heartbeats and lease timing (proposed values for PRD §20 budgets)

| Signal            | Interval            | Consequence                                                                                                                                                                                                                 |
| ----------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker heartbeat  | 10 s                | `stale` after 30 s without one; shown in UI                                                                                                                                                                                 |
| Job lease extend  | every 5 s; TTL 30 s | The extend response carries the cancel flag. Cancellation reaches the worker within about 5 s, and the worker stops new probes immediately (target ≤10 s). A disconnected worker's lease expires within 30 s (target ≤60 s) |
| Result submission | per batch           | Accepted only for the current `lease_id` (§7.1). A late or stale lease gets 409, and the result is quarantined                                                                                                              |

## Consequences

- One more key (the scope-signing key) to keep and rotate, besides the worker CA key and the plugin-signing key (ADR-0007). Key custody must be documented for self-hosted operators.
- A worker without the customer's local ceiling relies entirely on the control plane's scope. The UI must show whether a ceiling is configured.
- Strict parsing rejects some legitimate-but-unusual target notations. That is a deliberate trade toward safety.

## Security implications

- **Defends against:**
  - stolen enrollment tokens (single-use, short-lived, hashed);
  - copied credentials (the key never leaves the host, certificates are short-lived, revocation is immediate);
  - cross-tenant job access (ADR-0005 claim filter);
  - SSRF into metadata, loopback or the control plane;
  - DNS rebinding, IPv4/IPv6 notation tricks, redirect escapes;
  - late results after cancellation or revocation.
- **Does not defend against:** a fully compromised control plane (mitigation: local ceiling), a compromised worker host (it can lie about its own tenant's results; THREAT_MODEL TM-3-3, accepted risk), or a malicious first-party plugin bypassing the connector (TM-5-2, addressed by the probe/evaluate split in INITIAL_ARCHITECTURE §5.4).

## Required tests

- Enrollment token reuse, expiry and revocation.
- Wrong CA pin.
- Revoked worker: 401, all leases cancelled, a late result rejected.
- Expired certificate cannot renew.
- Tampered lease payload, wrong key ID, wrong `worker_id`, expired lease, clock skew.
- **Destination fixtures**, each asserted with packet capture (PRD AC-07):
  - `127.0.0.1`, `2130706433`, `0x7f.1`, `127.1`, `[::ffff:127.0.0.1]`, `169.254.169.254`;
  - a hostname resolving to a private address with only external authorization;
  - DNS rebinding (first answer in scope, second answer `127.0.0.1`);
  - a redirect to an out-of-scope host;
  - a redirect to an IPv6-mapped loopback;
  - a port not in the lease;
  - an exclusion inside an authorized CIDR;
  - a local ceiling narrower than the lease.

## Implementation notes (2026-11-08, M3, uncommitted; status stays PROPOSED)

Control-plane side only; no worker exists yet. `engines/api/src/vulnex/targets.py` implements §5 steps 1-5 (strict IPv4 parsing, IPv6 refusal, never-allowed ranges, scope membership with exclusions) and is the single parser for scope entries and assets. The worker (M4) is meant to import the same module for target expansion, so the parse rules cannot drift between the two sides. Two v0 limits are deliberate: a scope entry is at most a /8, and one asset range is at most a /20. Hostname assets are matched by name only; their resolved addresses must still be checked against the CIDR entries at connection time (§5.6), which is M4 work. The scope authorization is stored as an attestation bound to a SHA-256 digest of the exact entries (`app.scope_group.attested_digest`); this is the input to the signed scope lease, not the lease itself.
