# ADR-0005: Database-enforced tenant isolation

- **Status:** PROPOSED (prepared under founder decision D6, 2026-11-06). Not approved and not implemented.
- **Date:** 2026-11-06 · **Author:** Claude · **Approver:** Founder · **Reviewers:** Astra 6 (security review requested); GPT-6 when available
- **Addresses founder D6 conditions:** (c) database-enforced tenant isolation, (d) RLS context handling and cross-tenant testing
- **Related:** PRD SEC-02, FR-01, AC-03 · THREAT_MODEL TM-2-1, TM-2-2, TM-3-4 · [ADR-0001](ADR-0001.md)

## Context

Every scan result reveals a customer's weaknesses. Cross-tenant exposure is the worst failure VULNEX can have. The PRD requires PostgreSQL Row-Level Security (RLS) unless an ADR justifies an equivalent alternative. Self-hosted v0 will usually hold one tenant, but SaaS (later, D2) and MSP use cases hold many, and the schema must not have to change between them.

## Problem

How do we make cross-tenant reads and writes impossible even if one application query forgets its tenant filter, without leaking tenant context between pooled connections or background jobs?

## Alternatives considered

1. **Application filtering only** (`WHERE tenant_id = :t` in every query). A single forgotten filter leaks data, with no second line of defense. Rejected by PRD SEC-02.
2. **Database or schema per tenant.** Strong isolation, but migrations, connection pools and backups multiply per tenant, which is impractical for many small MSP tenants on modest hardware. Kept as a future option for regulated customers who demand it.
3. **Shared tables + RLS + composite foreign keys + application authorization.** Recommended: defense in depth at three layers.

## Decision (proposed)

### 1. Schema rules

- Every tenant-owned table has `tenant_id uuid NOT NULL REFERENCES tenant(id)` and `UNIQUE (tenant_id, id)`.
- Every reference from one tenant table to another is a **composite foreign key** `(tenant_id, x_id) REFERENCES x (tenant_id, id)`. The database therefore rejects a row in tenant A that points at a row in tenant B, regardless of RLS.
- Tenant tables live in schema `app`. Global vulnerability intelligence lives in schema `intel`, holds no customer data and has no RLS. The job queue lives in schema `queue` (§4).

### 2. Roles

| Role            | Login                 | Owns              | Rights                                                                                                 | RLS                                                   |
| --------------- | --------------------- | ----------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| `vulnex_owner`  | migrations only       | all schemas       | DDL                                                                                                    | Table owner; subject to RLS anyway because of `FORCE` |
| `vulnex_app`    | API and runner        | nothing           | DML on `app` (no UPDATE/DELETE on append-only tables), SELECT on `intel`, EXECUTE on `queue` functions | Enforced; `NOBYPASSRLS`, `NOSUPERUSER`                |
| `vulnex_ingest` | runner ingestion only | nothing           | DML on `intel` only; no access to `app`                                                                | n/a                                                   |
| `vulnex_queue`  | NOLOGIN               | `queue` functions | Cross-tenant claim/sweep (§4)                                                                          | Owner of `queue.job`                                  |

The application never connects as a superuser or as the owner. The connection strings and passwords are secrets injected at runtime (ADR-0002, no secrets in the repository).

### 3. RLS policy and tenant context

```sql
CREATE FUNCTION app.current_tenant() RETURNS uuid
  LANGUAGE sql STABLE
  AS $$ SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid $$;

ALTER TABLE app.asset ENABLE ROW LEVEL SECURITY;
ALTER TABLE app.asset FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON app.asset
  USING (tenant_id = app.current_tenant())
  WITH CHECK (tenant_id = app.current_tenant());
```

- **Fail closed:** without a tenant set, `current_tenant()` is NULL and `tenant_id = NULL` matches no rows. `NULLIF(…, '')` handles the empty-string value a custom setting can hold after a `SET LOCAL` has ended (empirically TESTED on PostgreSQL 17 on 2026-11-07: after a transaction-local `set_config` ends, the reused connection reads `''`, and `current_tenant()` returns NULL. See `engines/api/tests/test_database.py`. Astra 6 should still confirm it against the PostgreSQL docs).
- **Setting context:** at the start of every transaction, the API runs `SELECT set_config('app.tenant_id', :tenant_id, true)`. The third argument `true` makes it transaction-local, like `SET LOCAL`, and unlike `SET LOCAL` it accepts a bind parameter, so there is no string concatenation. The value is reset automatically at commit or rollback, so a pooled connection cannot carry it to the next request (TM-2-2).
- **Where the tenant comes from:**
  - users: the session's selected membership, re-checked against `membership` on every request;
  - service tokens: the token's tenant;
  - workers: the worker record behind the certificate (ADR-0006);
  - background jobs: the job row's `tenant_id` (§4).
    The tenant ID is never taken from a request body or URL alone.
- **Pre-tenant lookups** (login, memberships, worker identity) happen before a tenant is known. They go through narrow `SECURITY DEFINER` functions that return only the minimum: `app.memberships_for_user(user_id)` returns (tenant_id, role), and `app.worker_by_cert_fingerprint(fp)` returns (worker_id, tenant_id, status). Each function has a fixed `search_path` and is reviewed like an API endpoint.

### 4. Queue across tenants

The runner claims background jobs from all tenants, and workers claim jobs only from their own tenant. `queue.job` is owned by `vulnex_queue` and is not directly accessible to `vulnex_app`. Access goes through `SECURITY DEFINER` functions:

- `queue.claim_for_worker(worker_id, limit, ttl)`: derives tenant and scope group from the worker record inside the function, and touches worker queues only
- `queue.claim_for_runner(queue, owner, limit, ttl)`: runner queues only; may return any tenant's jobs; never worker queues
- `queue.extend(job_id, lease_id, ttl)`
- `queue.complete(job_id, lease_id, outcome)`
- `queue.request_cancel(job_id)`
- `queue.sweep()`

Every returned job carries its `tenant_id`. The caller then opens a separate transaction with that tenant set before touching any `app` table. A worker's claim scope is derived from its authenticated record **inside** the database function, so no caller argument can widen it. Queue semantics are in [INITIAL_ARCHITECTURE §7.1](../architecture/INITIAL_ARCHITECTURE.md).

### 5. Application layer

RLS is the second line, not the first. FastAPI dependencies check role permissions (PRD §10) on every route. A record belonging to another tenant returns **404**, never 403. There is no cache in v0 (ADR-0001), so there is no cache-key leakage to design for yet. Exports are generated and served inside the tenant's transaction context.

### 6. Required tests (CI gates; DEFINITION_OF_DONE)

All run against real PostgreSQL in Docker, as `vulnex_app`, never as owner.

| Test               | Asserts                                                                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RLS coverage       | A catalog query lists every table in `app` with a `tenant_id` column. Each must have `relrowsecurity` and `relforcerowsecurity` true and a policy. A new table without them fails CI                                     |
| No-context read    | With no tenant set, `SELECT` on every `app` table returns 0 rows                                                                                                                                                         |
| Cross-tenant write | With tenant A set, inserting a row with `tenant_id = B` fails `WITH CHECK`; inserting a child that references a B parent fails the composite foreign key                                                                 |
| Route matrix       | A test enumerates every FastAPI route. Each tenant-bearing route must have a two-tenant test (tenant B's credentials against tenant A's IDs → 404 or empty; no write succeeds). A route missing from the matrix fails CI |
| Pool leakage       | Interleave many concurrent requests for tenants A and B on a small pool and assert that no response contains the other tenant's rows                                                                                     |
| Background jobs    | A job for tenant A cannot read or write tenant B's rows; a worker claim never returns another tenant's job                                                                                                               |
| Definer functions  | Each `SECURITY DEFINER` function returns only its documented columns and rejects unexpected input                                                                                                                        |
| Role privileges    | `vulnex_app` cannot `UPDATE`/`DELETE` append-only tables, cannot `SET ROLE` to the owner, and has no `BYPASSRLS`                                                                                                         |

## Consequences

- Every query pays a small RLS predicate cost. Each `tenant_id` gets an index (usually the leading column of composite indexes). Measure against the PRD §20 latency budget before tuning.
- ORM convenience is slightly reduced: composite foreign keys must be declared explicitly in SQLAlchemy models.
- `SECURITY DEFINER` functions are privileged code and a review hotspot.
- Self-hosted single-tenant installs run the same code path. That is deliberate: there is one tested path.

## Security implications

- **Protects against:** a forgotten application filter, a mis-built join, a request with a forged ID, tenant context leaking through a pooled connection, cross-tenant writes.
- **Does not protect against:** a compromised database owner or superuser, the self-hosted operator (PRD §10), bugs in `SECURITY DEFINER` functions, or an application bug that sets the **wrong** tenant (mitigated by deriving the tenant only from authenticated identity and testing it).
- Backups contain all tenants. Backup access is an operator-level trust boundary (THREAT_MODEL TB8).

## Migration considerations

- RLS, roles and functions are created in the first Alembic migration, so no table ever exists without them.
- Moving a large or regulated tenant to its own database later (alternative 2) is possible because every row already carries `tenant_id`.
